KNOTRA — ТЕКСТ ВЫСТУПЛЕНИЯ
Исходный план: 5 минут. Дополнительный слайд GitHub Community: 30 секунд.

1. KNOTRA · 00:00–00:25
Knotra — открытый движок для процессов с AI-агентами. Мы заранее описываем шаги: где нужна модель, где запускается код и где требуется человек. Движок выполняет этот граф и сохраняет состояние каждого запуска. Покажем, для каких задач мы его делаем, как проверяем результат и куда развиваем архитектуру.

2. ЗАЧЕМ KNOTRA · 00:25–01:00
Если нужно исправить баг или разобраться в незнакомом коде, удобно открыть Codex и работать с агентом. У Knotra другой основной сценарий: один и тот же порядок действий нужно повторять для множества входящих задач. Например, каждая заявка поддержки проходит классификацию, подготовку ответа, проверку и при необходимости согласование. Мы задаём граф, доступные инструменты и лимиты, а затем получаем отдельный запуск с историей для каждой заявки. Codex тоже можно автоматизировать через SDK. Наше предложение — уже готовый движок таких процессов, с типизированными шагами, Desktop, CLI и выбором модели, включая локальную через Ollama.

3. ГРАФ ПРОЦЕССА · 01:00–01:45
Граф хранится в YAML. В нём описаны зависимости и контракты данных: что шаг получает и что должен вернуть. Модель может подготовить ответ, код — проверить его, условие — выбрать ветку, а человек — согласовать результат. Для исправлений есть цикл с заданным пределом. В проекте девять типов узлов, включая вложенные процессы и обработку коллекций. Агент выбирает действия внутри своего шага, а правила перехода между шагами остаются в графе. Проверка формата данных при этом не заменяет проверку фактов: для неё нужно написать отдельный код или добавить согласование.

4. ПРИМЕР: ИГРА · 01:45–02:35
Эту игру написала небольшая локальная qwen3.5:9b через Ollama. Мы не ограничились просьбой написать крестики-нолики: Knotra автоматически запускала фиксированные тесты и возвращала ошибки модели вместе с кодом. Модель исправляла код, а пайплайн проверял его снова. В показанном repair-прогоне мы специально подали ошибочную стратегию. Исправление прошло 3159 проверок на 929 позициях со второй итерации, после чего отдельный sandbox проверил и собрал HTML. Генерация с нуля тоже прошла, в отдельном запуске. Один ответ на промпт сам по себе не подтверждает работоспособность игры. Здесь готовность определяют тесты, которые модель не может менять. Исправление не гарантировано: при исчерпании лимита попыток запуск завершается ошибкой и не выдаёт готовую игру.

5. ПРИМЕР: ПОДДЕРЖКА · 02:35–03:15
Представим поддержку интернет-магазина: покупатель спрашивает, где его заказ. Сначала код проверяет входные данные. Затем агент через MCP запрашивает клиента, заказ и историю обращений, чтобы понять проблему. Второй агент обращается к базе знаний и правилам компании, подбирает решение и готовит ответ. Код проверяет ссылки и заданные ограничения. Граф отправляет типовой ответ сразу, а сложный случай или ошибку проверки передаёт оператору. Оператор может исправить текст и разрешить отправку. Агенты имеют доступ к чтению данных; ответ отправляет отдельный инструмент после проверок. У каждого обращения свой запуск с историей. Это схема применения Knotra: MCP-серверы и API поддержки нужно подключить отдельно.

6. АРХИТЕКТУРА · 03:15–03:55
Движок и CLI написаны на Go, интерфейс — на React и Tauri. River доставляет задания через PostgreSQL, а Knotra определяет готовность шагов, права и бюджеты. База хранит состояние и события; отдельное хранилище — файлы и сохранённые результаты. Поэтому можно закрыть Desktop и позже подключиться к тому же запуску. При восстановлении движок использует сохранённые ответы. Если результат внешнего вызова неизвестен, требуется явное решение оператора. Модель выбирается в подключениях: можно использовать API или локальную Ollama. На своей инфраструктуре нужны и база, и файловое хранилище, и средства исполнения шагов.

7. МАСШТАБИРОВАНИЕ · 03:55–04:30
Если компания хочет обрабатывать десятки тысяч обращений в сутки, важно распределять работу между машинами. Мы развиваем Knotra в эту сторону: одна система, общая очередь в PostgreSQL, общее хранилище файлов и несколько нод с исполнителями. Например, каждое обращение поддержки создаёт запуск одного и того же пайплайна. Внутри движка роли уже разделены. Сегодня тест подтвердил работу трёх отдельных процессов: они завершили 18 workflow с 54 вызовами; после штатной остановки одного два других продолжили работу. Тест шёл на одной машине с фиксированными ответами модели. Многомашинное развёртывание ещё нужно довести, а десятки тысяч в сутки — целевой сценарий, не измеренная производительность.

8. GITHUB COMMUNITY · 04:30–05:00
Knotra заметили и за пределами команды: о проекте написал Telegram-канал GitHub Community. На предоставленном скриншоте у него 154882 подписчика, то есть больше 150 тысяч. В посте показали наш интерфейс и дали ссылку на GitHub. Для нас это способ получить вопросы и отзывы от тех, кто пробует автоматизировать похожие задачи.

9. ИТОГ · 05:00–05:30
Knotra имеет смысл там, где нужен повторяемый процесс: шаги известны, результаты нужно проверить, а часть решений оставить человеку. Уже есть движок, Desktop, CLI и примеры с игрой, исследованием и проверкой релиза. Начать можно локально с Ollama и Docker; код и инструкции открыты на GitHub под MIT. Дальше хотим довести распределённый запуск и проверить его на реальной нагрузке. Если у вас есть похожий процесс, интересно обсудить, какие этапы и проверки в нём нужны.
