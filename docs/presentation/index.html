Knotra — открытый движок для процессов с AI-агентами. Мы заранее описываем шаги: где нужна модель, где запускается код и где требуется человек. Движок выполняет этот граф и сохраняет состояние каждого запуска. Покажем, для каких задач мы его делаем, как проверяем результат и куда развиваем архитектуру.

Например, каждая заявка поддержки проходит классификацию, подготовку ответа, проверку и при необходимости согласование. Мы задаём граф, доступные инструменты и лимиты, а затем получаем отдельный запуск с историей для каждой заявки. Codex тоже можно автоматизировать через SDK. Наше предложение — уже готовый движок таких процессов, с типизированными шагами, Desktop, CLI и выбором модели, включая локальную через Ollama.

Типизированные входы и выходыДвижок проверяет формат данных перед следующим шагом.

Все 9 типов в движкеllm · agent · tool · code · switchhuman · pipeline · foreach · loop
Граф хранится в YAML. В нём описаны зависимости и контракты данных: что шаг получает и что должен вернуть. Здесь показан один пример: агент готовит ответ, код проверяет его, условие выбирает дальнейший путь, человек согласует результат. Последняя карточка обозначает выходные файлы, это не отдельный тип узла. Всего в движке девять типов, они перечислены внизу: llm, agent, tool, code, switch, human, pipeline, foreach и loop. Llm вызывает модель, agent может выбирать инструменты, tool выполняет один вызов. Pipeline запускает вложенный граф, foreach обрабатывает коллекцию, loop повторяет шаги в пределах лимита. Проверка формата данных не заменяет проверку фактов: для неё нужны отдельные проверки.

Реальный артефакт Knotra · работает офлайн

Эту игру написала небольшая локальная qwen3.5:9b через Ollama. В демонстрационном repair-прогоне мы специально подали ошибочную стратегию. Тест нашёл последовательность ходов, на которой компьютер проигрывал. Knotra вернула модели эту ошибку вместе с кодом и автоматически проверила исправление. Со второй итерации тесты прошли. Они проверяют правила игры, допустимость ходов и стратегию, затем отдельный sandbox проверяет и собирает HTML. В отчёте сохранены 3159 проверок на 929 позициях: это объём тестирования игры, а не оценка модели или число попыток. Один ответ на промпт не подтверждает работоспособность. Готовность определяют фиксированные тесты. При исчерпании лимита попыток запуск завершается ошибкой и не выдаёт игру. Генерация с нуля тоже прошла, в отдельном запуске. Запись от 5 октября 2026, источник: docs/verification.md.

Пример обращения

«Где мой заказ?»

У каждого обращения — свой запуск и история.

Агенты читают данные через MCP. Право отправить ответ есть только у финального шага.

Представим поддержку интернет-магазина: покупатель спрашивает, где его заказ. Сначала код проверяет входные данные. Затем агент через MCP запрашивает клиента, заказ и историю обращений, чтобы понять проблему. Второй агент обращается к базе знаний и правилам компании, подбирает решение и готовит ответ. Код проверяет ссылки и заданные ограничения. Граф отправляет типовой ответ сразу, а сложный случай или ошибку проверки передаёт оператору. Оператор может исправить текст и разрешить отправку. Агенты имеют доступ к чтению данных; ответ отправляет отдельный инструмент после проверок. У каждого обращения свой запуск с историей. Это схема применения Knotra: MCP-серверы и API поддержки нужно подключить отдельно.

Запуск сохраняется независимо от открытого окна Desktop.
Локальная модель через Ollama или API-провайдер — на выбор.

Движок и CLI написаны на Go, интерфейс — на React и Tauri. River доставляет задания через PostgreSQL, а Knotra определяет готовность шагов, права и бюджеты. База хранит состояние и события; отдельное хранилище — файлы и сохранённые результаты. Поэтому можно закрыть Desktop и позже подключиться к тому же запуску. При восстановлении движок использует сохранённые ответы. Если результат внешнего вызова неизвестен, требуется явное решение оператора. Модель выбирается в подключениях: можно использовать API или локальную Ollama. На своей инфраструктуре нужны и база, и файловое хранилище, и средства исполнения шагов.

Если компания хочет обрабатывать десятки тысяч обращений в сутки, важно распределять работу между машинами. Мы развиваем Knotra в эту сторону: одна система, общая очередь в PostgreSQL, общее хранилище файлов и несколько нод с исполнителями. Например, каждое обращение поддержки создаёт запуск одного и того же пайплайна. Внутри движка роли уже разделены. Сегодня тест подтвердил работу трёх отдельных процессов: они завершили 18 workflow с 54 вызовами; после штатной остановки одного два других продолжили работу. Тест шёл на одной машине с фиксированными ответами модели. Многомашинное развёртывание ещё нужно довести, а десятки тысяч в сутки — целевой сценарий, не измеренная производительность.
